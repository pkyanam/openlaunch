---
title: Pairing, access and permissions
description: Use a short-lived setup token to pair one device, connect agents separately, then approve device functions and revoke access when needed.
---

## Create a device setup token

In **Devices → Add device**, create a device setup token. It uses the `ol_sdk_` prefix, expires after 10 minutes by default, and can attach one device by default. Copy it when shown; the console cannot show it again. This token is for setup only: it cannot authenticate an agent, call MCP tools, or approve grants.

Setup exchanges the token for a separate private credential stored by the device. That child credential remains valid after the setup token expires or is revoked. The setup token is never saved in the device identity.

## Connect an agent separately

Use an admitted OAuth connection such as ChatGPT or Codex, or create a named agent API connection in **Connections**. Agent API credentials use the `ol_agent_` prefix and have read or action access. They cannot pair devices. Keep agent credentials out of device setup and device identity storage. A new connection starts with action access to all current and future workspace functions; you can exclude specific devices or functions in its access policy, and an explicitly read-only connection stays read-only. Existing connections keep their previously selected mode and grants until you explicitly broaden them.

You can also invite an agent as a named workspace member with **Connections → Agents**: a one-time invitation admits that exact verified AgentID identity with an operator or administrator role. See [agent connections](/agents) for the full flow.

## Grant device functions

An attached device appears in **Devices**. Open its **Access** view and choose which agent connection may call which functions. A grant can have a time limit or remain active until you revoke it. The setup token itself cannot operate anything, and an agent credential cannot approve its own grants. What changes with pairing is inventory: a newly attached device becomes callable by connections and members with an all-functions access policy — the default for new connections and invited agent members — unless you exclude that device or function. Connections in selected-functions mode still need an explicit grant, and a changed function manifest clears earlier grants; review and grant the updated functions again for those connections.

Revoking an agent connection removes its grants and stops its agent requests. Revoking a setup token prevents future use of that token, but does not invalidate a child credential already issued to a paired device. Remove a device from **Devices** to revoke its child credential. You can revoke one device grant without revoking the agent connection or removing the device.

## Safe retries and action results

Device attachment uses a request ID saved before setup begins. If the network drops, rerun the same setup command with the same token within 10 minutes so the service can return the same device identity. If that retry window expires, inspect **Devices** before starting a new setup.

Actions expire after their time-to-live. Devices poll the bridge about every 10 seconds. `queued` and `received` are intermediate states; check for a terminal result before deciding an operation succeeded. A disconnect or lost reply can leave the physical outcome uncertain. The service does not promise exactly-once hardware execution.

## Older integrations

Older combined connection records remain supported for compatibility. New setups use a device setup token and a separate agent OAuth or API connection; do not create a legacy combined token for a new integration. The older one-use enrollment code flow remains for existing clients. See the [SDK guide](/sdk).

## Hardware checks

Software pairing does not prove a physical board acted. Confirm the real device result, then test grant boundaries, expiry, reconnect, duplicate requests and revocation on each supported setup. See the [verification guide](/status) for current hardware acceptance status.
