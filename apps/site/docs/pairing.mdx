---
title: Pairing, access and permissions
description: Pair agents and devices with one SDK token, then approve device functions separately and revoke each credential when needed.
---

## Create one SDK token

In **Connections**, create a named token and choose read or action access and an expiry. To use it for device setup, enable device attachment and set a limit of 1–20 devices. The default is one device for seven days. Copy the token when shown; the console cannot show it again.

The same token can authenticate an SDK agent and attach new devices. Device attachment creates a separate, private credential for each device. The setup command keeps the SDK token out of the device identity file.

## Grant device functions

An attached device appears in **Devices**. Open its **Access** view and choose which agent connection may call which functions, then set a grant expiry. Pairing alone does not grant function access, and a token cannot approve its own grants. A changed function manifest clears earlier grants; review and grant the updated functions again.

Revoking an SDK token removes that connection's grants, stops its agent requests and blocks future attachments. A device already attached stays paired until you remove it from **Devices**. Removing a device revokes its private device credential. You can also revoke one device grant without revoking the connection or removing the device.

## Safe retries and action results

Device attachment uses a request ID saved before setup begins. If the network drops, rerun the same setup command with the same token within 10 minutes so the service can return the same device identity. If that retry window expires, inspect **Devices** before starting a new setup.

Actions expire after their time-to-live. Devices poll the bridge about every 10 seconds. `queued` and `received` are intermediate states; check for a terminal result before deciding an operation succeeded. A disconnect or lost reply can leave the physical outcome uncertain. The service does not promise exactly-once hardware execution.

## Older integrations

The one-use enrollment code flow remains for older clients. It is bound to a workspace, can be used once, and expires after 10 minutes. Use the SDK token flow for new integrations; see the [SDK guide](/sdk).

## Hardware checks

Software pairing does not prove a physical board acted. Confirm the real device result, then test grant boundaries, expiry, reconnect, duplicate requests and revocation on each supported setup. See the [verification guide](/status) for current hardware acceptance status.
