| Component | Responsibility |
| --- | --- |
| TypeScript protocol, authorization and core | Device manifests, enrollment, grants, command expiry and lifecycle |
| HTTP and MCP packages | Shared API handlers and agent tools |
| React owner console | Pairing, capability grants and action inspection |
| Node and SQLite local bridge | Local development service and persistent state |
| Cloudflare Worker and Durable Objects | Hosted API, Clerk verification and workspace-isolated SQLite persistence |

## Identity and permissions

Clerk verifies hosted console sessions and agent OAuth tokens. Google and AgentID are sign-in providers; email/password sign-in is disabled. AgentID verifies the agent's identity through Clerk and does not automatically share a human owner's workspace. Different Clerk accounts remain isolated. OAuth uses PKCE and resource audiences. Owners register custom clients under Connections with exact callbacks and a read/action ceiling; admission checks the verified user's workspace registry on every request. Built-in clients remain configured separately. Console sessions and agent API/OAuth credentials have separate roles. See [AgentID sign-in](/agents#sign-in-with-agentid).

A workspace owner can admit an AgentID agent as a named member through a one-time invitation bound to that exact verified Clerk subject; the membership identity is a hash of the verified Clerk issuer and subject, with no email linking and no retrieval of AgentID owner claims. Roles are owner, administrator and operator: only the owner delegates administration, administrators onboard and manage agents, and operators get runtime device control only. Members are managed via **Connections → Agents**, the workspace API and compact MCP tools (`workspace_invite`, `workspace_agents`, `policy_update` and others) that re-check the live policy on every call.

An owner creates separate credentials for device setup and agent access. A short-lived `ol_sdk_` setup token attaches devices only; an `ol_agent_` API connection authenticates agents only. Each attachment receives its own private device credential, which remains valid after the setup token expires or is revoked. The setup credential cannot operate anything, but a newly attached device becomes part of workspace inventory: connections and members with an all-functions access policy — the default for new connections, new OAuth registrations and invited agent members — can call its functions without a further per-device step, subject to owner-set exclusions. Existing untyped combined connection records remain supported for compatibility but are not offered for new integrations. Connections in selected-functions mode keep the legacy behavior: the owner grants selected functions on each device with an expiry or until revoked, a credential does not approve its own grants, and a changed manifest revokes those grants. OAuth scopes authorize API operations but do not create device grants. Read-only connections never gain write access, and the service checks the current access setting and device grant whenever an agent calls a tool, including a custom function discovered earlier. Legacy one-use enrollment remains available for older integrations.

Hosted workspace storage uses SQLite-backed Durable Objects identified from the verified Clerk issuer and user identity. A workspace cannot use another workspace's device records or grants.

## Manifests and command delivery

A device manifest can describe custom functions with a name, title, description and input schema. Schemas support a root object with bounded strings, bounded numbers or integers, and booleans. Additional root properties and external references are rejected. Each manifest can contain up to 64 functions for Home Assistant linked devices, 24 for Linux or 16 for other kinds, with up to 16 parameters per function; custom definitions cannot replace built-in capabilities. After an owner grants a function, it appears as a device-specific MCP tool. The live grant is checked again when the tool runs.

Devices fetch commands over outbound HTTPS and report correlated results. Node and native Go adapters subscribe to authenticated, payload-free work hints for prompt polling, with ten-second polling as a fallback. The Roomba Uno polls every second. Commands move through queued, received and terminal states, and expire within a bounded lifetime. Pending MCP receipts instruct agents to check the same action until it finishes. If a device disconnects or an acknowledgment is lost, the service may not know whether the physical action occurred. There is no exactly-once execution guarantee.

`POST /v1/broadcasts` can request an action for up to 20 devices. Each device receives its own action or error result; a broadcast is not an atomic operation.

## Trust and device support

Model output cannot grant itself permission. The service checks API scopes and per-device grants. Device credentials are separate from provider credentials. Cloudflare is a trusted relay: TLS protects each network hop, rather than encrypting an action end-to-end from the model host to hardware.

R4 credentials are plaintext in EEPROM; Pi credentials use a restricted local file. Physical compromise can expose them. Commands are typed and bounded; unrestricted shell access and arbitrary LAN proxying are not default capabilities.

The Pi health profile reports process health; the [Linux host profile](/linux) adds locally configured files, fixed commands, system metrics and user services. GPIO and Pi display control are not implemented. Uno R4 firmware supports health, its built-in LED and matrix text; a separate Roomba sketch exposes robot controls. See [verification](/status) for physical acceptance and remaining checks.

## Deployment

The hosted API and public documentation website are separate services. Cloudflare Pages serves the site and read-only `/docs-mcp`; the Cloudflare Worker and Durable Objects serve authenticated device controls. `www.openlaunch.dev` serves the website, and the apex redirects to `www`. Vercel remains authoritative for DNS.

WebSocket wake hints are implemented. OTA signing and rollback, durable event subscriptions, broader quotas and account lifecycle controls are future work. D1 and R2 are design options, not deployed dependencies.

See the canonical [architecture document](https://github.com/pkyanam/openlaunch/blob/main/docs/architecture.md) and [verification record](/status) for implementation and acceptance details.

[Home Assistant](/home-assistant) linked functions additionally accept bounded nested JSON objects for native service data and targets. Their MCP catalog uses stable discovery and generic invocation to avoid thousands of cached per-entity tools; every granted function remains callable.
