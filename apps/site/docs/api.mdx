The web console, MCP and device clients use the same command service and permission checks.

## Authentication

Owner management uses an authenticated Clerk owner session. Google is the enabled sign-in provider; email/password sign-in is disabled. Agent MCP uses an admitted OAuth client, the correct resource audience, `openlaunch:read`, and separate capability grants. `openlaunch:act` permits action requests but does not create a device grant. OAuth uses PKCE.

Agents and device adapters use an owner-created SDK token (`ol_sdk_…`). Choose read or action access, an expiry, and whether it can attach devices with a limit of 1–20. The same token can authenticate an SDK agent and attach devices. Each attached device gets a separate credential, and function grants remain separate. Legacy `ol_agent_` tokens can still authenticate agents but cannot attach devices. See the [SDK guide](/sdk) for the short setup path.

Device polling and result reports use a private per-device bearer credential. Never compile an SDK token into a firmware image or put it in prompts or logs. USB provisioning may temporarily retain the bootstrap token while attachment is pending; the maintained adapters clear it after saving and verifying the child identity. Device identity files contain only the child credential. Legacy enrollment-issued credentials remain supported. Keep every credential out of source control.

| Method | Route                           | Purpose                                                                 |
| ------ | ------------------------------- | ----------------------------------------------------------------------- |
| GET    | `/healthz`                      | Service health; not a device result                                     |

| POST   | `/v1/sdk/devices`               | Attach a device using an SDK token and stable request ID                |

| POST   | `/v1/sdk-tokens/{id}/revoke`    | Owner revokes a token, its grants and future attachment access          |

| POST   | `/v1/device/enroll`             | Device exchanges an enrollment for its credential                       |
| GET    | `/v1/grants`                    | Owner lists active saved grants                                         |
| POST   | `/v1/grants`                    | Owner approves agent/device/capability access                           |
| POST   | `/v1/grants/revoke`             | Owner revokes that agent's access to a device                           |

| POST   | `/v1/devices/{id}/actions`      | Request a supported capability                                          |
| POST   | `/v1/broadcasts`                | Request an action for up to 20 devices, with a result for each          |

| GET    | `/v1/device/{id}/events`        | WebSocket connection for payload-free device wake hints                 |
| POST   | `/mcp`                          | Stateless device MCP requests                                           |

## Create an SDK token

An authenticated owner sends `POST /v1/sdk-tokens` with:

```json
{
  "name": "workbench agent",
  "access": "act",
  "ttlSeconds": 604800,
  "canAttach": true,
  "deviceLimit": 1
}
```

`access` is `read` or `act`; the token lifetime is 60–2,592,000 seconds. Set `canAttach` to allow device setup and choose `deviceLimit` from 1 to 20. Save the returned token in protected storage; listing tokens never returns the secret again. The token cannot approve its own function grants. Revoking it removes the agent's grants, cancels its queued actions and blocks later attachments. Already attached devices remain paired until separately removed by the owner.

The older `/v1/agent-connections` route names remain aliases for existing clients; tokens created through those legacy routes cannot attach devices.

## Attach a device

An SDK token with attachment enabled sends `POST /v1/sdk/devices` with a function manifest and UUID request ID:

```json
{
  "requestId": "2fd1a6d4-d177-4ec9-9f0f-e2d5ad5368d9",
  "manifest": {
    "name": "Workshop sensor",
    "kind": "custom.rp2040",
    "capabilities": ["device.health"],
    "functions": []
  }
}
```

The response contains `deviceId` and a private child credential `token`. Keep those in the device's protected identity store; do not persist the SDK token there. A retry must use the same request ID and identical manifest for 10 minutes to recover the same attachment. After that, inspect the device inventory before starting another request. Attaching does not grant the token's agent access to device functions.

## Publish device functions

A device authenticates with its own credential and sends `{ "manifest": ... }` to `POST /v1/device/{id}/manifest`. Its kind must match attachment. Publishing an identical manifest keeps grants intact. A changed manifest removes previous device grants, cancels queued actions and marks outstanding received actions uncertain. The owner approves the functions again. Use the SDK's `publishManifest()` or adapter CLI `publish` command rather than copying credentials into commands.

## Download activity

In the console, open Activity → Download full history. The JSON file includes
all retained receipts, function arguments and results; keep it in private storage.
The normal Activity list shows the latest 100 actions.

`GET /v1/actions/export` requires an owner session and returns
`{ "data": { "format": "openlaunch.actions.v1", "exportedAt": 0, "actions": [] } }`.
`exportedAt` is a Unix timestamp in milliseconds. Internal idempotency metadata
and device credentials are excluded. Agents cannot export owner history.

A workspace retains up to 5,000 actions. At that limit, new actions are rejected
with HTTP 429. Downloading is a copy and does not remove actions or free capacity;
saved requests continue to prevent accidental duplicate execution. History
archiving is not currently available.

## Request an action

```json
{
  "capability": "led.set",
  "arguments": { "on": true },
  "idempotencyKey": "your-unique-request-id",
  "ttlSeconds": 60
}
```

Built-in capabilities are `device.health` with `{}`, `led.set` with `{ "on": true }`, and `display.text` with `{ "text": "hello" }`. A device must advertise and implement the requested capability. Pi currently reports health; Uno implements all three.

TTL is 1–300 seconds. Reuse an idempotency key only for an identical request. A conflicting duplicate is rejected. Devices poll every 10 seconds, so allow enough time for delivery.

## Device wake hints

The Node adapter can request a one-use ticket with its per-device credential from `/v1/device/{id}/events-ticket`. The ticket expires after 30 seconds and is offered in the WebSocket `Sec-WebSocket-Protocol` header for `/v1/device/{id}/events`; it is not sent in the URL. The WebSocket sends only a small work hint, never action arguments or results. On a hint, the adapter checks for the action through the normal HTTPS poll endpoint. The Node runner keeps its 10-second HTTP polling fallback. Go, Uno and ESP32 continue to use HTTP polling every 10 seconds.

## Custom device functions

A device can advertise custom functions in its manifest with a name, title, description and input schema. Schemas accept a root object with bounded string, number, integer or boolean fields. Additional root properties and external schema references are rejected. Each manifest supports up to 16 functions and each function up to 16 parameters; a custom function cannot replace a built-in capability.

The owner grants each custom function to an agent through the console. Granted functions appear as device-specific MCP tools. The service checks the current grant each time one is called, so a previously discovered tool stops working after its grant is revoked.

## Broadcasts

`POST /v1/broadcasts` accepts up to 20 device IDs and a capability request, including its arguments, idempotency key and TTL. It returns an independent action or error for each device. A broadcast is not atomic: devices can accept, reject or complete the action independently. Inspect each action result.

## Responses and errors

REST success responses use `{ "data": ... }`. Errors use `{ "error": { "code": "...", "message": "..." } }`; validation errors also identify invalid fields. HTTP 202 means accepted into the queue, not physically completed.

Inspect the returned action ID. `queued` and `received` are intermediate states. Terminal states distinguish success, failure, cancellation and expiry; an uncertain delivered outcome must not be reported as success. See [pairing and permissions](/pairing) for the lifecycle.
