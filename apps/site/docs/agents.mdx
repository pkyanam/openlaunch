Any OAuth-capable MCP host can connect to openlaunch. Agents can also use the openlaunch SDK with an `ol_agent_` API connection. Device setup uses a separate short-lived `ol_sdk_` token and cannot authenticate an agent. New agent connections can use all current and future workspace functions by default; owners can exclude devices or functions. Existing selected-function grants and read-only limits are preserved.

## Sign in with AgentID

Choose **Continue with AgentID** on the [console sign-in page](https://www.openlaunch.dev/console/). Clerk uses AgentID's standard OpenID Connect flow to verify the agent's identity. If the browser is not enrolled, AgentID provides the enrollment instructions. Use your own AgentMail account; never paste its key into openlaunch or a conversation.

AgentID is a sign-in provider, while openlaunch OAuth and API connections authorize device access. Signing in with a different Clerk account opens a separate workspace. The agent's identity and its human owner's identity are distinct; openlaunch does not merge workspaces by email or automatically share the owner's devices.

To control devices in an existing workspace, its owner can admit your agent as a named member: the owner sends a one-time workspace invitation, and your agent accepts it while signed in with AgentID. A new member gets an all-functions policy — every current and future workspace device and function, unless the owner excludes specific devices or functions — at the invited operator or administrator role. Administrators can invite and manage other agents; operators get runtime device control only. Owners and administrators manage members through the console, the workspace MCP tools (`workspace_invite`, `workspace_agents`, `workspace_agent_revoke`), or the workspace API. Existing legacy connections keep their previously selected mode and grants until the owner explicitly broadens them.

Without a membership, the workspace owner can authorize your MCP host through OAuth or create a separate agent API connection. Review its policy in **Connections → Agents**. AgentID sign-in alone does not share another identity's workspace. Device setup tokens remain attach-only. Connect the MCP host to `https://www.openlaunch.dev/mcp`, or use its agent API connection with `ol login`.

## Executor and custom OAuth clients

Open **Connections → OAuth clients**, enter the application name and its exact callback URLs, and choose read access or read-and-action access. **Use Executor settings** fills `https://v2.executor.sh/api/oauth/callback`. Register a public PKCE client when your host supports it; its optional secret field stays empty. A confidential client uses PKCE plus a secret shown once. Copy that secret before leaving the tab; openlaunch does not store it.

Enter the client ID, optional secret, and `https://www.openlaunch.dev/mcp` in your MCP host. Request `openlaunch:read` and, for commands, `openlaunch:act`. Clients may also request openid, profile, email and offline_access within the registered ceiling. Complete OAuth sign-in and consent, then review exclusions in **Connections → Agents**. Newly registered clients default to all-functions access, within their scope ceiling. Existing selected-function clients still need device grants.

For Executor apps, declare the command scopes explicitly in the app's `provider.ts`:

```ts
oauth: oauth2({
  discover: "https://www.openlaunch.dev/mcp",
  scopes: ["openlaunch:read", "openlaunch:act", "offline_access"],
})
```

Executor's automatic discovery otherwise inherits the initial read-only Bearer challenge. An online device can therefore expose only its read functions even when its owner saved all function grants. After changing the provider, sign in again and select the resulting account in the app's profile; an existing authorization cannot gain scopes by refreshing its token. Confirm `list_functions` includes the granted write functions before requesting a command. Choose only `openlaunch:read` for an intentionally read-only app.

Registered clients belong to the owner's workspace. Revoking a client immediately blocks its openlaunch access, removes its function grants and cancels undispatched commands, even if authorization-provider cleanup needs a retry. To change callback URLs or scope ceilings, revoke the client and register a replacement. Local servers without a hosted authorization provider support agent API tokens instead.

## MCP compatibility

The device and documentation endpoints support the [2026-07-28 MCP specification](https://modelcontextprotocol.io/specification/2026-07-28) and earlier handshake-based clients. Modern requests use per-request protocol metadata and the matching `MCP-Protocol-Version`, `Mcp-Method` and, for named calls, `Mcp-Name` headers. `server/discover` reports supported versions and implemented capabilities. The local stdio adapter forwards these fields too.

Device MCP provides tools; documentation MCP provides read-only tools and page resources. Optional prompts, sampling, elicitation, subscriptions and extensions are not advertised. Device operations return queued receipts, which require a subsequent status read; they are not protocol tasks or proof of physical success. Permission-dependent discovery has a private cache scope and a zero TTL, and every invocation checks current grants.

## ChatGPT and Codex

Use the device MCP endpoint `https://www.openlaunch.dev/mcp` and approve the connection through Clerk. Review ChatGPT or Codex in **Connections → Agents**. New workspaces use all-functions access by default; existing workspaces preserve their saved grants until you explicitly choose all-functions access. The downloadable [openlaunch plugin](/downloads/openlaunch-plugin.zip) includes this endpoint and the separate documentation MCP.

For Codex CLI:

```sh
codex mcp add openlaunch --url https://www.openlaunch.dev/mcp --oauth-client-registration cimd
codex mcp login openlaunch --scopes openid,openlaunch:read,openlaunch:act --oauth-client-registration cimd
```

OAuth consent and device grants are separate. Call `list_functions` for the current grants and schemas, then `invoke_device_function` to use a granted function. These tools are available even before any device grants, so newly approved functions remain callable when the client caches its tool list. Clients connected before these tools were added need to refresh their MCP tools once.

## Any agent with the API connection

In **Connections**, create a named agent API connection and choose read or action access. Set a finite expiry or choose until revoked. Its credential uses the `ol_agent_` prefix and is shown once. Provide it to your agent through a secret environment variable; never put it in a prompt, source file, shell command, or log. Revoke it in Connections to stop agent requests and remove its grants. A newly created connection starts with action access to all current and future workspace functions (with owner-set exclusions); an explicitly read-only connection stays read-only, and legacy connections keep their previously selected grants.

Install the SDK archive and use `createClient({ url, token })`. The client lists accessible devices and `listFunctions()` returns their permitted built-in and custom functions with input schemas and bounded `guide` text. The schema is authoritative; guide text does not authorize access or add device behavior. The client can request permitted functions and read or cancel actions. All-functions policies cover new devices automatically. Selected-function policies require grants that may expire or remain active until revoked.

```sh
npm install 'https://www.openlaunch.dev/downloads/openlaunch-sdk.tgz'
```

See the [Bridge SDK guide](/sdk) for a minimal code example, action lifecycle, and adapter interface.

## Agent CLI

Install `ol` on your PATH, then log in with AgentID:

```sh
{{cli-install}}
ol login --agentid
ol devices list
ol functions list
```

Open a new terminal and restart your agent application after installing. The browser-backed login verifies your agent's AgentID identity and saves an identity-bound credential privately on this computer (`0600`); use `ol login` instead to paste a separate agent API credential from Connections. `OPENLAUNCH_AGENT_TOKEN` from a secret store overrides saved login. Device setup and owner credentials remain separate. See the [CLI guide](/cli) for workspace selection, custom JSON arguments, idempotent retries, action watching, cancellation and logout.

## Codex on your computer

For the local MCP bridge, start with [Get started](/setup). For the default installation:

```sh
codex mcp add openlaunch -- node ~/.local/share/openlaunch/scripts/local-mcp.mjs
```

The adapter reads only its protected agent credential. It never forwards your owner session key or device setup token. Restart Codex or refresh its MCP connections, then ask it to list the devices you granted.

## MCP connections

Hosted MCP uses OAuth. Other agents can use an `ol_agent_` API connection. Keep the owner session key and `ol_sdk_` device setup token private; an agent must never use either. Agent connection expiry, device grants and device credentials are separate controls; see [Pairing and permissions](/pairing).

## Device tools

Call `list_functions` to read the current built-in and custom function catalog, including each device ID, capability name, exact input schema and guide. Call `invoke_device_function` with that device ID, capability, arguments, a fresh idempotency key and an optional TTL. It can invoke every granted function, including `roomba.clean`, even if a device-specific tool is absent from the client's cached tools. Revoking access takes effect on the next call. Device-specific tools remain available when the client discovers them.

For example, after an explicit cleaning request and a live `roomba.clean` grant:

```json
{
  "deviceId": "YOUR_DEVICE_ID",
  "capability": "roomba.clean",
  "arguments": { "mode": "standard" },
  "idempotencyKey": "YOUR_FRESH_REQUEST_KEY",
  "ttlSeconds": 30
}
```

Pass this object to `invoke_device_function`. The board's local interlocks still apply, and a Roomba success receipt confirms serial transmission rather than physical cleaning. The stable device tools are:

| Tool                     | Purpose                                             |
| ------------------------ | --------------------------------------------------- |
| `list_functions`         | Read current granted functions and exact schemas    |
| `invoke_device_function` | Queue any granted built-in or custom function       |
| `list_devices`           | List devices visible to this connection             |
| `request_device_health`  | Ask a device for a fresh health result              |
| `set_led`                | Set the Uno's built-in LED                          |
| `show_text`              | Display up to 96 ASCII characters on the Uno matrix |
| `get_action`             | Read the actual action outcome                      |
| `cancel_action`          | Cancel an action that has not been delivered        |

An action ID is a receipt number, not proof that the board acted. Ask the agent to check `get_action` until it reaches a terminal result.

The maintained hardware integrations currently cover Uno R4 WiFi and Raspberry Pi. An agent can use any device family that has an openlaunch adapter and manifest; the bridge does not require a built-in profile for a custom kind. Start with the [custom function guide](/functions) to publish bounded functions for another board or setup.

## Documentation for agents

The website has a separate, read-only MCP endpoint at `/docs-mcp`, built with Blume. It supports searching docs, reading pages, listing pages, and inspecting navigation. It needs no device credentials and cannot operate boards.

Each page is also available as Markdown: append `.md` to its URL. The website publishes `/llms.txt`, `/llms-full.txt`, `/skill.md` and `/.well-known/mcp.json` for discovery. The docs menu offers PDF and EPUB export; **Listen to this page** uses your browser's voices.
