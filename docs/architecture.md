# openlaunch architecture

## Monorepo boundaries

- `apps/cloud`: Cloudflare Worker for hosted API requests, Clerk identity checks and workspace-isolated SQLite Durable Object storage
- `apps/local`: persistent local developer bridge, bound to loopback by default
- `apps/site`: product website, searchable guides, Markdown downloads and read-only documentation MCP
- `apps/web`: React owner console for pairing, permissions and action inspection
- `packages/sdk`: typed agent/device clients and a custom adapter CLI; independent of board libraries and agent providers
- `packages/protocol`: capability, device manifest and request contracts
- `packages/core`: enrollment, device identities, grants, command lifecycle, expiry and revocation
- `packages/authorization`: shared authorization helpers
- `packages/http`: transport-neutral HTTP handlers
- `packages/mcp`: agent-facing tools using the official MCP SDK
- `devices/pi`: Go runtime for Linux ARM64/ARMv7
- `firmware/uno-r4-wifi`: Arduino C++ firmware with pinned board core and libraries
- `integrations`: host-specific integration guidance, independent of firmware
- `scripts`: build orchestration, simulated E2E flows and USB provisioning

JavaScript packages use npm workspaces and one lockfile. Go and Arduino keep their native toolchains; root npm tasks orchestrate them. Provider credentials stay off devices.

## Identity, pairing and permissions

Clerk provides hosted account sign-in and agent OAuth. The console uses Clerk's provider-aware sign-in component for Google and AgentID (`oauth_agentid`), including callbacks and verification. AgentID is upstream identity verification, not a device credential or grant. Different Clerk subjects remain separate workspaces; AgentID owner claims do not link a human workspace or confer its permissions. The hosted service verifies console sessions and OAuth access tokens against the configured Clerk issuer; it does not accept raw AgentID tokens. OAuth uses PKCE and resource audiences; built-in agent identities are configured explicitly. Owners register other OAuth clients in Connections with exact callbacks, a read/action ceiling, enforced PKCE and consent. Admission requires an active client record in the verified user's workspace; it never derives from model-supplied metadata. Client secrets are returned once and excluded from workspace storage and audit. Email/password sign-in is disabled. See [AgentID setup](AGENTID.md).

Owner sessions and agent identities are separate. An owner creates an `ol_agent_` API connection with read or action access and a finite or until-revoked lifetime, or admits an agent through OAuth. These agent credentials cannot attach devices. Device setup uses a separate short-lived `ol_sdk_` token, attach-only, with a default lifetime of 10 minutes and a default limit of one device. Attachment returns a private child credential; the setup token is not saved in the device identity, and the child credential remains valid when its setup token expires or is revoked. Removing the device revokes its child credential. Existing untyped combined connection records remain supported for compatibility, but new integrations must use separate setup and agent credentials. Legacy board-bound enrollment codes remain single-use and expire after 10 minutes.

The setup credential itself cannot operate anything: it only attaches, and it cannot authenticate agent requests. What changes with attachment is workspace inventory. A newly attached device becomes available to agent policies in all-functions mode without a further per-device step, while connections in selected-functions mode need the owner's explicit grant. The owner separately grants functions on each device for selected-mode connections, for a bounded period or until explicitly revoked; a token cannot grant itself. Read-only agent connections cannot issue commands. Revoking an agent connection removes its grants and stops its API access.

New linked, API and OAuth connections default to action access with all current and future workspace functions available, including newly attached devices and newly approved functions such as Home Assistant discoveries; owners opt out by excluding specific devices or functions. A connection's explicit read ceiling stays on the connection itself, so a read-only connection remains read-only even under an all-functions policy. Exclusions cannot be lifted by the member itself or through child credentials, whose policies are always intersected with their live parent chain. Pre-upgrade connections and admitted built-in clients keep their legacy grant-only behavior until the owner sets an explicit policy; broadening one requires an explicit owner choice.

## Agent workspace membership

AgentID sign-in can go beyond a separate workspace: a workspace owner or delegated administrator admits an agent as a named member through a one-time workspace invitation bound to that exact verified Clerk subject. Membership is an admission record, not a credential; access still flows through verified sign-in sessions or identity-bound CLI credentials issued by that sign-in, and raw AgentID tokens never authenticate the device API or MCP. No email auto-merge exists.

Roles are owner, administrator and operator. Only the owner delegates administration. Administrators onboard and manage agents; operators get runtime device control only and cannot manage membership or lift their own exclusions. New members default to an all-functions policy at the invited role; an already-active member cannot accept a fresh invitation to reset its role or exclusions (the request fails with `409 conflict`), so the owner edits the policy or revokes and re-invites. Revoking a member denies all functions immediately, revokes any agent connection bound to that member, and is recorded in the audit log. The `ol login --agentid` browser-backed PKCE exchange issues a 24-hour `ol_agent_` credential with its own all-functions policy, no local exclusions, the member's role at mint time as its ceiling, and a live delegation link to the member's policy — parent exclusions, selected-mode grants, role changes and revocation take immediate effect, and no parent snapshot is copied. Joining does not auto-select the workspace: a scoped API/OAuth credential's select call returns the target without persisting the identity default, and only a verified browser session's selection saves it, so the CLI requires `ol login --agentid --workspace WORKSPACE_ID`, because an issued credential stays bound to the workspace it was minted for. The membership identity is a hash of the verified Clerk issuer and subject, so the service requires no retrieval of AgentID owner claims or email bindings. The hosted MCP endpoint exposes the same management surface through compact named tools (`workspace_invite`, `workspace_agents`, `policy_update`, `onboarding_status` and others) that re-check live policy on every call and allow no generic proxy or self-escalation. See [agent workspace onboarding](AGENT-ONBOARDING.md).

The hosted service derives each workspace's SQLite Durable Object identity from the verified Clerk issuer and user identity. Within that object, individual records are stored in native SQLite and changed rows commit together in a transaction; polling does not rewrite the entire action ledger. The first access migrates the earlier KV snapshot, preserves a backup and installs a guard that prevents an older Worker from using stale permissions. See the deployment guide before rolling back this storage change. Requests are isolated by workspace. Agent requests are checked for their OAuth scope or `ol_agent_` API access and a live per-device function grant on each call, including calls made through previously discovered custom-function tools. A persistent grant remains active until the owner revokes it. An ungranted action and an agent's attempt to grant itself are rejected; device attachment separately authenticates the `ol_sdk_` setup token and enforces its device limit.

The shared core admits new records within a 16 MiB logical storage budget, including reserved capacity for pending command results and the bounded audit ring. Quota checks apply to every transport before growth is committed. Already received results and access revocation remain available when a legacy workspace exceeds the limit; new work and queued dispatch pause. Idempotent retries return their existing receipt without using additional capacity.

## Commands and device functions

An authorized MCP request becomes a typed, bounded action. Devices initiate outbound HTTPS polls, receive commands and report correlated results. Queued, received and terminal states are distinct. Expiry and revocation are enforced by the service. If a device disconnects or loses an acknowledgment, the physical outcome can remain unknown; the system does not promise exactly-once execution.

Devices may advertise functions in their manifest. Definitions include a name, title, description and input schema. Supported input fields are bounded strings, bounded numbers or integers, and booleans in a root object that rejects additional properties. Manifests are limited to 64 functions on Home Assistant linked devices, 24 on Linux and 16 on other kinds and 16 parameters per function, reject external schema references and cannot replace built-in capabilities. An owner can grant custom functions individually; approved functions are returned by the stable `list_functions` MCP tool and can be called through `invoke_device_function`, even when a host caches its original tool list. They also appear as device-specific MCP tools during discovery. Both invocation paths check current grants and exact device argument schemas on every call.

The `POST /v1/broadcasts` endpoint can request the same action for up to 20 devices. It returns an independent action or error for every device, so a broadcast is not an atomic multi-device operation.

## Device SDK boundaries

The cloud service accepts bounded custom device kinds without a board-specific service change. A device adapter owns its hardware drivers, credential storage, manifest and execution. The shared protocol owns attachment, polling and correlated results. Attachments use a durable request UUID and manifest fingerprint; a lost response can recover the same identity within 10 minutes. The service derives the child credential with a versioned, server-only HMAC keyring, stores only its hash, and rejects expired or changed retries rather than creating another device. Agent integrations use the same API and grants; `GET /v1/functions` returns only the advertised built-in and custom functions the current agent may call, with exact device schemas and bounded explanatory guidance. Provider credentials never reach firmware.

Linux and desktop custom adapters can use the Node SDK and its setup/publish/run CLI. The maintained Go runtime has a lightweight Pi health profile and an opt-in [Linux host profile](LINUX-HARNESS.md) with scoped files, named commands, metrics, user services and owner-enabled shell/desktop control. Local policy is independent of cloud per-function grants. Policy revisions revoke previous grants, including changes behind existing aliases. Native microcontroller adapters speak the same HTTPS contract, using platform TLS and storage. Pi, Uno and standalone ESP32 setup use the same attach-only `ol_sdk_` setup token. USB helpers prompt for credentials and configure runtime storage; secrets are not compiled into sketches. An ESP32 development board is not the Uno R4 connectivity coprocessor; support for one must not alter the other's transport firmware.

The Node runner, Go Pi runtime and Uno firmware keep durable result journals so a failed result upload can retry the saved outcome without rerunning the hardware handler. This reduces duplicate work after interruption but does not promise exactly-once physical execution.

Manifest changes require updated grants for selected-function connections; all-functions policies cover the new catalog unless excluded. They revoke prior device grants, cancel queued commands and preserve uncertainty for commands already received. A schema describes implemented behavior; advertising a function cannot install a driver or make an unsupported board operation work.

## Trust boundaries and runtime support

Cloudflare is a trusted relay. TLS protects each network hop; it does not provide end-to-end encryption from the model host to the board. R4 credentials are stored in plaintext in EEPROM; Pi credentials use a restricted local file. Physical compromise can expose them. Commands are typed and bounded; unrestricted shell access and arbitrary LAN proxying are not default capabilities.

The Go Pi health profile reports process health; the Linux host profile adds real host operations with an unprivileged user policy. Its GPIO adapter is not implemented; owner-enabled Linux desktop capture/input is separate from hardware display control. Uno R4 firmware supports health, the built-in LED and matrix text. Runtime acceptance on physical boards—including network, TLS, provisioning, power-loss and reconnect behavior—is still pending. Health and simulated results must not be represented as successful physical actions.

## Delivery and deployment

The Node and native Go adapters use an authenticated WebSocket as a wake signal. Its one-use ticket expires after 30 seconds and is passed in the WebSocket handshake header. The channel sends only a payload-free work hint; adapters read actions and report outcomes over HTTPS. Ten-second HTTP polling remains as a fallback. Go drains queued commands after an acknowledged result with a 100 ms wait; hints never override pending-result retry backoff. Generic Uno and ESP32 runtimes poll every 10 seconds; the Roomba Uno sketch polls every second, reuses its TLS connection for completely framed responses and closes it on errors. JSON API responses declare their UTF-8 byte length so embedded clients need not wait for stream closure. New receipts retain the first server result timestamp; Activity separates queue and receipt delays. No timing field proves physical completion. The hosted bridge uses a Cloudflare Worker and one SQLite-backed Durable Object per workspace. The public documentation site is a separate Cloudflare Pages deployment; its `/docs-mcp` endpoint serves read-only documentation tools and does not control devices.

The public website is served at `www.openlaunch.dev`; the apex redirects to `www`. Vercel remains authoritative for DNS. The hosted service and website deployments are independent. See [website deployment](WEBSITE-DEPLOYMENT.md) for deployment and domain details.

WebSocket wake hints are deployed for the Node adapter; extending event-driven wakeups to firmware remains future work. OTA signing and rollback, durable event subscriptions, broader quotas and account lifecycle controls also remain future work. D1 and R2 are design options, not deployed dependencies.

## Development and acceptance

Local software development uses the console and simulated Go device with local persistence and disposable development credentials. Deployed acceptance on commit `6e317a0` covered the then-current legacy combined SDK-token flow: stable attachment retries after a lost response, non-persistence of the master token, no default grants, forbidden ungranted actions and self-grants, quota rejection, owner grants, manifest-change revocation, and Node WebSocket wake hints followed by HTTPS action checks. These results do not verify the current split token-purpose routes or persistent-grant option. The 601 ms health and 508 ms `custom.echo` results came from a software fixture, not physical hardware. See the [verification page](../apps/site/docs/status.mdx) for the current record; physical board acceptance remains separate.

The hosted bridge folds recent authenticated WebSocket auto-response timestamps into device presence before inventory and action admission. This keeps long-running Linux commands online while HTTPS polling is paused, without waking the Durable Object for pings or adding idle HTTP traffic. Only open sockets with matching device attachments count; revoked devices, stale or future timestamps cannot revive presence. This does not dispatch or acknowledge work, change expiry, or relax grants.

The Linux runner additionally uses `POST /v1/device/{deviceId}/heartbeat` every 20 seconds only during long execution as an HTTPS fallback. This authenticates the separate device credential and updates presence without fetching another command, touching the journal or extending expiry. Short operations and idle polling issue no additional heartbeat requests.

## Home Assistant gateway

A gateway is a normal outbound device identity with an explicitly owner-approved linked-device quota. Home Assistant runs locally in the SDK's `openlaunch-ha` runner or the HA OS app in `integrations/home-assistant`. Its local HA credential is separate from its openlaunch credential; neither is present in manifests or agent responses. Setup tokens remain attach-only.

The gateway discovers REST states/services and reads device/entity/area registries through a short-lived authenticated HA WebSocket. Registry access failures are reported explicitly; entity/service discovery remains available. Each entity, registered device and integration-wide service becomes a stable linked record with `gatewayId` and `gatewayKey`. Entity targets are fixed locally. Native service data accepts bounded JSON objects; HA validates its own selector semantics. Integration-wide services have separate grants and explicit targets where required. No arbitrary URL proxy or shell is exposed by this adapter.

The parent publishes inventory in bounded batches, polls one existing action queue and reports child outcomes through its own credential. Only its direct children can use that transport. Child presence derives from gateway reachability; it does not prove physical readiness. Existing wake hints target the gateway for child work. Removing an entity revokes its grants; transient HA disconnection preserves them. Owner revocation cannot be undone by discovery. Revoking the parent revokes all children. Manifest changes still revoke affected grants.

The console's bulk gateway grant is owner-only convenience over existing per-device grants, restricted to current inventory. Future discovery never authorizes itself. The MCP catalog stays compact for HA installations: stable discovery and generic invocation expose every granted function rather than registering thousands of per-entity tools. API and CLI use the same contracts. HA service responses report acceptance and an optional observed state with `physicalVerified: false`. Durable journaling prevents replay after interrupted execution and retries saved receipt delivery; ambiguous writes stay explicitly unverified.

[Home Assistant](https://www.openlaunch.dev/docs/home-assistant) linked functions additionally accept bounded nested JSON objects for native service data and targets. Their MCP catalog uses stable discovery and generic invocation to avoid thousands of cached per-entity tools; every granted function remains callable.
