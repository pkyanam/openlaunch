# ArduRoomba API coverage for openlaunch

## Audit basis and model 551 status

This inventory is based on the locally authored ArduRoomba v4.0.2 checkout at
`/tmp/openlaunch-ArduRoomba` (HEAD `5120998`, release commit dated 2026-09-10),
including its public headers, implementations, README, examples, and host
protocol test. The library says it targets Create 2 and Roomba 500/600 series.
Roomba 551 is a 500-series model, so its documented family makes it a
reasonable compatibility target for the documented Open Interface commands.
The repository does not call out model 551, provide 551-specific traces, or
show a test on that hardware. Treat support as **expected by family, not
verified for model 551**. The [iRobot Roomba 500 Open Interface
Specification](https://cps-vo.org/sites/cps-vo.org/files/cpsvo_file_nodes/iRobot_Roomba_500_Open_Interface_Specpdf.pdf)
documents model-family packet and command behavior; it is the basis for the
adapter's 500-series packet allowlist, not proof that this particular 551 unit
or wiring has been tested. Validate the actual OI port, cable/power, BRC wake,
sensor packet behavior, and each exposed actuator on the target robot before
claiming hardware support. Examples also mention 700-series models, while the
supported-model section does not; that is not evidence of 700-series support.

The library's host test (`test/host/run.sh`) checks a small set of serialized
movement, LED, and brush command bytes. It does not qualify the sensor parser,
WiFi/BLE extensions, autonomous behaviors, safety routines, or model 551. Most
actuator methods return `void`; a successful serial write is not confirmation
that the Roomba accepted a command or moved. Report command delivery separately
from physical verification.

## Coverage decisions

“Network now” means the operation is suitable for a narrowly typed, per-function
grant through openlaunch after firmware applies the stated wrapper. “Wrapper
required” means the feature is useful and present in the library, but direct
exposure would inherit unbounded duration, blocking I/O, ambiguous failures, or
persistent physical effects. “Defer” means keep it off the agent-facing
manifest until a separate owner-controlled design covers recovery, consent, and
its physical consequences. These decisions concern the openlaunch agent API;
they do not remove features from the user's library.

## Implemented openlaunch coverage set

The fixedESP transport should carry typed openlaunch actions, not either library
extension's HTTP/BLE command string. This sketch implements these individually granted names:

1. `roomba.stop` and a bounded `roomba.drive` command, with ≤1000 ms local
   movement lease, radius translation, motor-state separation and local
   readiness checks. The default `serial_only` build does not read D6/D7;
   optional contact builds retain software permits. The bounded motion loop
   avoids network calls; autonomous contact checks can be delayed by HTTPS.
2. `roomba.sensor.read({packetId})` over the manufacturer's byte-sized packet
   table for IDs 7–15, 17–31, and 34–42. Return `valid` and bytes only on a
   complete read and local sample time. Firmware rejects 16 and 32–33 and
   drains bounded startup text before querying. Pre-query backlog can recover;
   a query timeout latches reads invalid until restart. Reads run only while idle.
3. Explicit `roomba.leds.set` with the Roomba 500/551 mask, fixed
   `roomba.song.play` (firmware defines fixed songs before playback), bounded `roomba.tone.play`,
   and separately scoped `roomba.brushes.burst` with a local off timer.
   `roomba.resume_safe` is a separately granted Safe-mode recovery
   operation; firmware must never expose Full mode.
4. `roomba.drive_direct` independently bounds both wheel velocities to ±150
   mm/s and stops after at most 1000 ms. Sequences remain deferred until step
   count and aggregate runtime can be bounded without losing stop handling.

5. `roomba.clean({mode})`, `roomba.dock`, and `roomba.pause` map the library's
   autonomous starts and a fixed Safe-mode stop sequence. Clean/dock actions are
   separately granted and checked for board readiness at start; optional
   contact builds additionally require local permission. They intentionally run
   on the Roomba's own autonomous behavior after serial transmission; an action
   expiry is not a run deadline. `roomba.pause` stops the current run by entering
   Safe mode, then zeroing drive and turning brushes off. It does not preserve a
   job to resume. No network result claims physical verification.

Keep power-off, Full mode, arbitrary OI commands, sensor IDs outside the
explicit 500-series allowlist, dynamic pin/serial configuration, and the
library's legacy/WiFi/BLE command parsers off the agent manifest. An HTTP
action's expiry or a queued stop cannot substitute for a physical stop circuit.

The serial-only policy is selected by the owner at build time, never by an agent argument. `RoombaLocalControl.h` retains an opt-in contact policy for installations that have D6/D7 switches. The default relies on the Roomba's native protections and local timed output stops; it has no separate held-to-run switch. Device health reports wiring/readiness and sensor-link state without sending a stop. Network, Arduino power/CPU failure or a broken UART can still prevent a stop from reaching the robot.
