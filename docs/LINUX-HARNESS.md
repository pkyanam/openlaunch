# Linux harness

The Go device runtime now has an opt-in `linux` host profile. It keeps the Pi health-only profile and all embedded transports intact. The public guide is [Linux host control](https://www.openlaunch.dev/docs/linux).

## Muse comparison

Baseline reviewed: [Muse Linux SDK at 74a5e2d](https://github.com/facebookincubator/muse-gadget-sdk/tree/74a5e2d7fc895f109f83a9a1dbed705dbcd8b1ff/linux). This comparison concerns the published Linux implementation, not unreleased Muse features. The implementation was written independently.

| Area                 | Muse Linux SDK                                                       | openlaunch Linux profile                                                                                                                                                                                                                        |
| -------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Published operations | `system.run`, `file.read`, `file.write`, `device.health`             | Up to 22 implemented functions (Linux catalog ceiling 24), adding directory management, file metadata and removal, upload abort, process inspection, network inventory, user services, optional shell, browser, screenshots, mouse and keyboard |
| Commands             | Bash command string, working directory, timeout                      | Fixed named argv by default; owner-enabled system.exec adds shell strings under the installing user, with deadlines                                                                                                                             |
| Files                | Absolute paths under the execution user's permissions; 64 KiB chunks | Explicit root aliases, read-only/write policy, rooted filesystem access; 2 KiB reads / 6 KiB writes / 2 MiB upload budget                                                                                                                       |
| Publication          | Chunked writes with optional SHA-256                                 | Required SHA-256 on final chunk, atomic create-if-absent and explicit revision-checked replacement                                                                                                                                              |
| Health               | Host metrics including uptime/load/memory/disk/model/temperature     | Host metrics plus separate adapter uptime, kernel/distribution and network/process functions                                                                                                                                                    |
| Agent access         | Muse pairing and account permissions                                 | Provider-neutral OAuth/API, exact per-function grants, dynamic API/MCP/CLI discovery; policy changes revoke grants                                                                                                                              |
| Installation         | System service, configured run-as account, phone/BLE pairing         | Verified standalone binary, hidden setup-token prompt, user PATH and optional user service; no sudo or BLE requirement                                                                                                                          |

openlaunch provides a broader set of structured host functions and independently enforceable local policy and cloud grants. Owner-enabled shell and desktop control are implemented. Larger transfer envelopes, BLE pairing and device-initiated chat remain outside this profile. Expanding those areas requires deliberate design rather than advertising unsupported behavior.

## Architecture

- `linux_policy.go`: private owner policy, manifest schemas and revision fingerprint. A manifest embeds the revision, so changing roots, argv or services requires reapproval even when aliases stay unchanged.
- `linux_files.go`: rooted file operations, private ordered upload staging, SHA-256, bounded transfer count/bytes, expiry and atomic publication. No recursive deletion or arbitrary absolute agent paths.
- `linux_exec.go`: strict device-side arguments, real Linux host metrics, procfs inventory, interface inventory, bounded subprocess output, remaining-TTL deadlines and process-group cancellation. No agent credentials or provider dependencies.
- `linux_control.go`, `linux_desktop.go`, `linux_wayland.go`: owner-enabled shell and desktop schemas; whitelisted session environment, persistent browser launch, bounded real JPEG capture and Wayland/X11 keyboard/pointer delivery. Wayland uses the official core registry and wlr virtual pointer protocol over the local user socket; capture uses grim and typing uses wtype. X11 uses scrot and xdotool. Only supported active sessions are accepted.
- `linux_cli.go`: local owner policy commands, single-runtime advisory lock and systemd user-service setup.
- `events.go`: authenticated one-use-ticket WebSocket wake hints with bounded frames, heartbeat, reconnect backoff and cancellation. Hints only wake HTTPS polling; they cannot execute actions or bypass result-retry backoff. The same channel already serves the Node adapter.
- Existing `main.go`: attach-only setup token exchange, child credentials, authenticated outbound polling and durable action/result journal. The `raspberry-pi-4` profile retains health-only behavior and gains optional wake notifications.

The shared function schema permits strings up to 8192 characters only for the `linux` kind. Other manifests retain their 1024-character ceiling. Linux manifests may have up to 24 capabilities; other kinds remain at 16. Authenticated Linux screenshot uploads permit a 64 KiB body and 48 KiB UTF-8 JSON result, backed by a pending-result reservation; other results and embedded request envelopes keep their existing limits. Linux response reading is bounded at 64 KiB to accommodate full action receipts, which echo arguments and their internal idempotency fingerprint; the Pi profile retains its 16 KiB response ceiling.

The installer and ARM64/ARMv7/x86-64 downloads come from the same CI commit as the site. No new cloud service or subscription is required. A new owner policy takes effect after runtime restart; startup publishes it before accepting new commands and fails closed if publishing or reconciling an existing result fails.

Rerunning the Linux installer upgrades the binary without attachment or policy initialization. It validates the private saved configuration, policy and journal first, then atomically replaces the verified executable under the existing runtime lock. Active user services stop and restart; failed starts restore the previous binary. Foreground runners must stop before replacement. Credentials, journal and upload staging are never restored from a stale snapshot or erased by update rollback. Existing unchanged manifests retain their grants.

MCP receipts expose action state and results without the internal owner-bypass marker. Pending receipts instruct the agent to check the same action until terminal or its deadline. Hosted Linux inventory guidance describes optional `model` and `temperatureC` fields without changing the device manifest or revoking existing grants.

## Acceptance

Run `npm run test:device` for real local filesystem, policy and subprocess tests, including traversal/link/special-file rejection, read-only roots, staged upload ordering/integrity/expiry, atomic create/replace, deadlines, duplicate delivery and exclusive runtime ownership. Run `npm run test:linux` on Linux for the same acceptance test used in CI (`scripts/linux-e2e.mjs`): actual host profile → authenticated local HTTP bridge → grant-filtered MCP → host execution → result receipt. Its disposable local software credentials are never production tokens.

On October 5, 2026, the owner's real Pi returned a successful cloud `system.info` receipt: Raspberry Pi 4 Model B Rev 1.5, ARM64, four CPUs, Debian 13, approximately 4 GB OS-visible RAM and 37°C. The old runtime waited 8.3 seconds for its idle poll; dispatch-to-receipt took 99 ms. This verifies basic hardware inventory, not the new notification/update path. Target acceptance still needs the upgraded runtime, a file round trip, an explicitly configured command, allowed user-service actions, reboot/reconnect and revocation. Do not advertise software tests as these physical checks. GPIO, system services, arbitrary LAN forwarding and device-to-agent chat are not implemented.

## Broad control and desktop acceptance

`openlaunch-host enable-control` enables shell and desktop together after checking the active session and installed helpers. `allow-shell` enables just shell; `disable-control` removes the broad controls. Optional control is omitted from legacy policy serialization, so a binary upgrade preserves the old policy fingerprint. Adding the new text/root functions changes the manifest and requires owner reapproval. Enabling or disabling it changes the fingerprint and requires restart and owner reapproval. The public guide contains the short setup and exact input fields.

Shell/input grants confer broad same-user access, including effects outside the structured file roots. No runtime sudo or root service is installed. Child commands receive only basic user/session variables, never a wholesale copy of the runner or systemd manager environment. Screenshots carry no authorization, and reported launch/input delivery is distinct from observed UI effects. Native MCP image content removes the base64 payload from its text channel; API/CLI retain it. Complete image outcomes stay durable until exact server acknowledgment; afterward their journal entries retain deduplication tombstones rather than the image bytes.

CI and local container acceptance run actual labwc and Xvfb sessions as a non-root user, capture and decode real JPEGs, send pointer/click/scroll/key events and verify typed text reaches a focused terminal. API/MCP software tests cover the larger image envelope, capability/kind restrictions, duplicate receipts, pending polling, quota reservation and read-only grants. Physical Pi desktop behavior remains owner acceptance after installing the update.

`file.root_info` reports an allowed root's real path and write policy. `file.write_text` is a bounded UTF-8 convenience over the same SHA-256-checked staging/publication code; agents need neither encoding nor checksum utilities. Defaults gain these two functions, so this release requires manifest reapproval even when legacy policy serialization is unchanged. Owner-enabled desktop setup adds the actual Desktop as a root when it exists and avoids private state; it never replaces an existing alias.

## Long commands and presence

The owner's October 5 voice session verified YouTube in returned Pi desktop screenshots, a 108.8-second VS Code installation with exit code zero, and successful scheduling of shutdown. VS Code was not launched after the owner requested shutdown; the receipt confirms scheduling, not physical power-off. The installation exposed a false-offline bug: synchronous execution paused HTTPS polling beyond the 45-second presence window. The cloud now reads authenticated hibernation ping timestamps before inventory/action admission, preserving idle cost and sequential command delivery. Existing socket-capable runners benefit without a binary update. Updated Linux runners add a presence-only HTTPS heartbeat every 20 seconds during long execution, covering an unavailable WebSocket without adding idle traffic.

The updated binary retains command output endings in stdoutTail/stderrTail as well as the beginning, with bounded JSON and accurate byte counts. Rerunning the standard installer preserves credentials, local policy and unchanged grants. Software acceptance advances beyond the online window with an unfinished action, checks that another request queues, and verifies socket reconnect and revocation.
